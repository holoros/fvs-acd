## Verdict

**The v12.11 model candidate: finalize as-is.** Both round-1 fixes (the RO Lever 4 cap and the
gated ESI-anchor height-cap re-clamp) are independently verified correct, complete, and inert on
every currently reported number. The byte-identical gate-off guarantee reconfirms on a fresh,
independently-constructed stand. No new model-code defect was found that changes a reported
benchmark number.

**The report and deck as they stand now, before the next update: finalize with fixes, not
as-is.** Three of the four analysis threads feeding the next report/deck revision have a
correctness problem that must be fixed before the numbers or the causal language go in: the
top-height-drift explanation already shipped in the current report cites a mechanism
(`esi.domht.afac`) that is not live code; the hardwood forest-group causal story is likely
misattributed to a QC-only harness artifact; and the NS long-interval headline currently rests on
a dead disturbance filter that leaves roughly a quarter of its own headline bucket contaminated
with undisclosed harvests. None of this is a case for reworking the lever architecture or
abandoning the NS or forest-group analyses; it is a case for fixing one data bug, correcting two
causal narratives, reconciling one set of disagreeing numbers already in the deck, and being
explicit about what is genuinely new evidence versus what is still an open question, before any of
it goes in front of Hennigar.

## Findings, ranked

### BLOCKER

**1. The NS long-interval disturbance screen is dead code (str/int comparison bug), and this
directly undermines the headline long-horizon claim.** `build_ns_long_bench.py` filters cut trees
with `raw["TREE_STATU"] == CUT_STATUS` where `CUT_STATUS` is a Python `int` (4), but
`pd.read_sas` returns `TREE_STATU` as a string column (`'1'`...`'5'`); `str == int` is always
`False` in pandas, so the tree-level cut screen silently drops zero rows every time it runs. The
philosophy-pass document reads this null result as corroboration ("every stand with a cut-flagged
year was already caught by SILVICULTU, 0 additional stands found"), when it is actually an
artifact of a filter that never executes. Independently recomputing the intended filter finds 756
of 3253 operational stands with a genuine `TREE_STATU=4` cut record, 454 of which are not caught
by the SILVICULTU-based screen the document does rely on, and cross-referencing those against the
actual scored pairs finds 603 of 4571 unmanaged pairs (13.2%) contain an undisclosed harvest inside
the interval, rising to **285 of 1210 pairs (23.6%) in the >30yr bucket**, the exact bucket driving
the reported bias sign-flip (+9.95% base / +7.23% candidate). A mid-interval harvest lowers observed
T2 volume without the model knowing, which mechanically manufactures apparent over-prediction in
the same direction and roughly the population size needed to explain some or most of the >30yr
sign flip. This is not ruled out by anything in the current document. **Fix:** correct the filter
(`raw["TREE_STATU"].astype(str).str.strip() == "4"`), rebuild the pair set, rescore the >30yr
bucket, and report the contamination rate whether or not it changes the sign-flip conclusion.
Nothing about the >30yr NS claim should be described as "clean, entirely unmanaged and
undisturbed" until this is done. Source: NS subagent verification, cross-checked against
`bench_ns_long_scorecard.csv` and `bench_ns_long_stand_counts.csv`.

### MAJOR

**2. The shipped report already attributes the in-domain top-height drift to a mechanism
(`esi.domht.afac`) that is not live code in v12.11, and conflates it with a different flag that
is genuinely live but unrelated in name.** Direct inspection of `AcadianGY_12.11.r` (both the
local mirror and the Cardinal copy, matching md5sums) shows `ops$use.esi.anchor.recal` and
`ops$esi.anchor.coef`, which the harness sets every run (`ops$use.esi.anchor.recal <- USE_ANCHOR`,
default `TRUE`) and which the harness's own comments and multiple project memos (20260708,
20260710, 20260718) describe as "the operational height fix" / "ESI-consistent dominant-height
anchor recalibration," **do not appear anywhere in `AcadianGY_12.11.r`** (`grep -c
"esi.anchor.recal\|esi.anchor.coef"` returns 0 on the authoritative Cardinal file). This mechanism
existed in the `AcadianGY_12.9.2.r` lineage (`calc_dht()`, confirmed at the documented line
numbers) and was apparently dropped somewhere in the 12.10.x/12.11 development without anyone
noticing; the harness still sets the now-inert ops values and still prints `ANCHOR%s=TRUE` in its
own diagnostic log, creating a false impression that ESI-consistent recalibration is running.
Separately, `ops$esi.domht.afac` (the variable the round-1 redteam's finding #2 names as "most
likely" the driver, citing NB_AFAC=0.579/QC_AFAC=0.111) is **never set** anywhere in the harness;
it is a different field that only the disabled `use.esi.domht` Chapman-Richards block reads, and
that block never executes (`ops$use.esi.domht <- FALSE`, confirmed hardcoded in
`bench_parity_split_ms_v1211.R` line 95, on Cardinal directly). The values NB_AFAC=0.579 and
QC_AFAC=0.111 are real and are live, but they feed a **third, different mechanism**: an
always-on, per-tree `dht.mult` column set directly from those env vars at tree-list construction
(`bench_parity_split_ms_v1211.R` line 139), multiplied unconditionally into every tree's height
increment (`dht = dht * dht.thin.mod * dht.sbw.mod * dht.hw.mod * dht.mult`, `AcadianGY_12.11.r`
line 1655). So the round-1 finding's top-level conclusion (top-height drift is not a lever effect,
six lever configurations give bit-identical topht) is well-supported and should stand, but the
**named mechanism in the write-up is wrong on two counts**: `esi.domht.afac` is not what's live,
and `esi.anchor.recal`/`esi.anchor.coef`, which several project memos call "the operational height
fix," is dead code that does nothing in this model file. This same NB_AFAC/QC_AFAC `dht.mult`
mechanism was independently flagged by the NS subagent as the thing the model's height-growth
anchoring is actually calibrated against (see finding 6). **Fix:** correct the GTR/report language
from "traced to the anchor calibration (esi.domht.afac)" to "traced to the always-on per-province
`dht.mult` height-increment scalar (NB_AFAC=0.579, QC_AFAC=0.111), not an ESI-consistent
recalibration mechanism, which does not exist in this model file." Separately, as a code-health
item outside this report's scope but worth a ticket: determine whether `use.esi.anchor.recal`
was intentionally dropped (in which case purge the dead ops flags and stop logging `ANCHOR=TRUE`
as if it means something) or accidentally lost in a refactor (in which case v13.1 should decide
whether to restore it before it ships with the same gap).

**3. The round-1 blocker's own stated justification for urgency was factually wrong, though its
conclusion and fix are fine.** Round-1 finding #1 states `ops$use.esi.domht` is "(v12.7.0, always
ON in the guardrail/candidate harness via `USE_ANCHOR=TRUE`)... it is always active in every
reported v12.11 number." This is false: `USE_ANCHOR` sets `ops$use.esi.anchor.recal` (dead code,
finding 2 above), not `ops$use.esi.domht`; the real harness hardcodes `ops$use.esi.domht <- FALSE`
unconditionally. Directly confirmed on Cardinal: `use.esi.domht in REAL harness candidate ops:
FALSE`. The later reframe document (`20260722_v1211_allsites_and_redteam_reframes.md`, reframe 5)
correctly walks this back ("off in all benchmark scoring, so it changes no reported number"), and
that corrected language is what actually made it into the shipped report and deck (confirmed by
the report/deck subagent, reframe 5 passes in the report text). So the end state is accurate, but
the chain of reasoning that got there conflated two similarly-named flags, and the "always active
in every reported number" claim, if anyone had cited it directly rather than the later correction,
would have been wrong. **Fix:** no report/deck change needed since the corrected language already
shipped; add a one-line note to the round-1 document itself (or a pointer to this round-2 document)
so the superseded justification does not get re-cited later as if it were the operative one.

**4. The forest-group hardwood-worsening claim is likely mis-attributed; the pooled effect is
dominated by a single source (QC MagPlot) whose shift is uniform across all three forest groups,
not hardwood-specific.** `v1211_forestgroup_scorecard.csv` confirms the headline numbers
(hardwood total-volume bias +2.82% base to +5.42% candidate) and the underlying accounting is
internally consistent (every forest-group n sums exactly to the matching all-sites n). But at the
source level, QC MagPlot's hardwood cell moves +35.05% to +42.67% (+7.62 points, the largest swing
and largest absolute bias in the whole table, on 115 of 462 pooled hardwood stands), and QC's
**softwood** cell moves -18.52% to -9.73% (+8.79 points) and **mixedwood** moves +1.84% to +9.69%
(+7.85 points) by comparable magnitude and the same direction in the same run. Lever 4 is a
hardwood-only mechanism and cannot touch softwood volume at all, so a uniform cross-forest-group
shift concentrated in one province is the signature of a source- or harness-level artifact, not a
hardwood-specific lever effect. This is the same class of problem the round-1 redteam already
diagnosed for the in-domain top-height drift (finding #2 there: "traces to...how the candidate's
mixed managed/unmanaged province split...differs from a single-pass base run," with an explicit
instruction to rerun the base config through the identical province-assembly procedure before
attributing anything to a lever) and that diagnostic step has not been applied here. Compounding
this, three different project documents offer three different, unreconciled explanations for
overlapping QC swings: the forest-group narrative blames recruitment/mortality levers outrunning
Lever 4; the all-sites "honest headline" blames Lever 2's management gate over-correcting basal
area relative to volume in Quebec; and round-1 finding #2 blames province-AFAC/harness-assembly
effects. On magnitude, the report's implied mechanism (recruitment and mortality levers "outrun"
Lever 4's derate) also overstates Lever 4's applied effect: the SPLIT-scored, population-average
derate actually applied at scoring is about 2.6% (round-1 finding #9, SM ≈0.974 multiplier), not
the roughly 13% worst-case per-species coefficient magnitude that gets casually cited as "Lever 4's
correction." **Fix:** before the GTR or deck states a causal story for the hardwood-group result,
rerun round-1 finding #2's prescribed diagnostic (base config through the identical
`cand_mixed` province-assembly, isolating harness-assembly effects from lever effects) applied to
the forest-group breakdown specifically, report the hardwood number with and without QC, and
reconcile the three competing explanations for the QC swing into one place. Source: forest-group
subagent verification against `v1211_forestgroup_scorecard.csv` and
`forestgroup_scorecard_v1211.R`.

**5. NS Claim A (site-index correction) generalizes an unmanaged-only null result to the managed
and overall bias, which were never re-scored with the corrected site index.** The +7.0 m ESI v8
raster bias figure is real and correctly cited (matches the underlying stress-test memo exactly:
job 12127451, n=40,596, bias +7.0, r=0.146). The unmanaged corrected-site re-score also checks out
arithmetically (raw base -6.04%/corrected -4.84%, raw candidate -6.07%/corrected -5.04%,
matching `bench_ns_scorecard.csv` exactly). But that re-score was run only on the unmanaged subset
(n=2347); the much larger managed (-58%) and overall (-41%) biases, where the interesting claim
actually lives, were never rescored with corrected site index at all. The document's own hedge
("a coarse basis-matching adjustment, not a precise per-plot recalibration") is honest, but two
paragraphs later the text draws a confident causal conclusion ("most of the -41% under-prediction
is REAL...regrowth response") that the data as gathered cannot support: a flat, spatially uniform
+7.0 m offset applied against a raster with r=0.146 (essentially no linear tracking of true site
index) cannot rule out a much larger, heterogeneous per-plot site effect hiding inside a
near-zero mean effect on the unmanaged subset, and the managed subset was simply never tested.
**Fix:** rescore the managed pairs with corrected site index before asserting the managed/overall
gap is "not primarily" a site-index artifact; until then, state the corrected-site finding as
applying only to the unmanaged subset, and describe the managed/overall attribution to disturbance
history as a hypothesis, not a demonstrated result. Source: NS subagent verification against
`bench_ns_site_esi.csv`/`bench_ns_site_esi_corrected.csv` and `bench_ns_scorecard.csv`.

**6. New transferability concern raised by the NS work, not yet disclosed: the model's live
per-province height-growth anchor (`dht.mult` from NB_AFAC=0.579/QC_AFAC=0.111) exists
specifically to counteract a scalar mean bias in an ESI input that explains almost none of true
site-index variance (r=0.146 against ground truth, per the NS document's own citation).** A single
mean offset correction cannot capture a raster's much larger unexplained per-plot error; the
correction is tuned to cancel bias on average, not to recover accuracy at the plot level. This
compounds finding 2: the mechanism actually doing the province-level height correction work is a
blunt multiplicative constant calibrated against a weak, mean-biased input, not a validated
ESI-consistent recalibration. Any future region or transfer relying on the same NB_AFAC/QC_AFAC
pathway (or any newly-derived AFAC for a new region, including a possible future NS-specific
factor) inherits this same unproven, poorly-constrained correction. **Fix:** add this as an
explicit model-transferability caveat (principle 7) in the GTR wherever NB_AFAC/QC_AFAC or a
future region-specific height-anchor factor is discussed; do not let the NS work's finding that
"the correction exists for a reason" read as validation that the correction is well-constrained.
Source: NS subagent, cross-validated independently by the main-thread code trace in finding 2.

**7. The Chapter-11 management-modifier out-of-sample numbers disagree between the report and the

PREVcomprehensive versions, so this is not a new regression) states 1.3 (installation-out) and 1.5
(province-out). PCT is 1.5 in the report versus 3.0 in the deck for the same installation-out
statistic, a two-fold discrepancy; the managed split-half figure is 5.2 in the report versus 5.6 in
the deck. These are exactly the numbers most likely to get cross-questioned in a live review.
**Fix:** trace both back to source (`mgmt_cv_robust.R` / `mgmt_finalfit.R` on Cardinal, per the
report's own Methods section) and reconcile to one number before the meeting, using the same
numbers-provenance-note convention Section 4 already applies to the three previously-disagreeing
"in-domain" figures. Source: report/deck subagent, direct text comparison.

### MINOR

**8. The postanchor fix eliminates the height-cap violation but not the underlying implausible
target curve, exactly as round-1's own recommended follow-up flagged, and that follow-up was not
done.** Independently reproducing round-1's blocker scenario on Cardinal (candidate ops, CSI 28,
`use.esi.domht` forced TRUE to exercise the gated path, 60-year run): without the fix, max tree
height reaches 65.00 m against a 50 m cap (15 m over) and topht oscillates non-monotonically across
years 40-60 (43.81, 39.53, 42.84, 44.64, 41.96); with the fix, max tree height is capped exactly at
50.00 m as intended, but topht is then pinned flat at exactly 50.00 m for all of years 40-60, an
unrealistic multi-decade plateau at the cap rather than a smooth asymptotic curve. The fix
correctly prevents the physically impossible overshoot and oscillation, but replaces it with a
different, still non-physical artifact (a hard clamp plateau), because round-1's own suggested
second step, reviewing whether the Chapman-Richards target curve is well-behaved above roughly
CSI 20-22 and age 100-120 (it reached 56.35 m at CSI 28/age 160 in round-1's own trace), was never
done. Zero practical risk today since `use.esi.domht` is off in every current benchmark run and the
now-dead `esi.anchor.recal` mechanism means nothing currently exercises this code path in
production scoring (finding 2), but it should not be left implicitly "fixed" for v13.1 or any
future config that turns the anchor back on. **Fix:** carry this as an explicit v13.1 watch item:
re-derive or cap the Chapman-Richards asymptote parameter for high-CSI, long-horizon cases, not
just the per-tree height cap. Source: main-thread direct verification on Cardinal
(`~/magplot/verify/redteam_round2/round2_checks.R`, ROUND2-E).

## What was independently verified and holds

- **Byte-identical gate-off**, reconfirmed on a genuinely novel stand not used in any prior smoke
  test or round-1 check (RO/QA/PB/RM mix, QC region, CSI 17, seed 20260722, 45-year projection):
  max|ddbh| = max|dht| = max|dexpf| = 0.000e+00, no row-count difference.
- **RO Lever 4 cap**, direct evaluation of `dht_hw_mod()`: RO's worst-case (form B, high risk)
  multiplier is now 0.8728, matching YB's 0.8728 essentially exactly (SM 0.8737), versus the old
  0.7334; the cap is implemented as described ("capped to the YB/SM field magnitude") and is
  mathematically consistent with the tribble values (RO spp.coeff.risk = 0.0220, matching YB's
  0.0220).
- **ESI-anchor height-cap re-clamp**, directly reproduced end to end: without the fix, a forced
  `use.esi.domht=TRUE` run at CSI 28 overshoots the 50 m cap by 15 m and produces a genuine
  non-monotonic topht oscillation; with the fix, the overshoot is eliminated (max height exactly
  50.00 m). The fix is syntactically and functionally correct for what it claims to do.
- **The fix changes no currently reported number**, confirmed directly on Cardinal:
  `ops$use.esi.domht` is `FALSE` in the real candidate ops built by the actual scoring harness
  (`bench_parity_split_ms_v1211.R`), and a 20-year run with the real candidate ops completes
  identically whether or not `use.htcap.postanchor` is set, because the gated block it lives in is
  never entered.
- **The report and deck carry no dropped content relative to their prior comprehensive versions.**
  Every section, table, and figure in the prior 306-line report and every slide topic in the prior
  23-slide deck is traceable in the current 1213-line report and 34-slide deck; no silent
  regression found.
- **Ten of ten spot-checked headline numbers** (CTRN, NB MagPlot, Maine FIA whole-plot and subplot,
  Baxter, softwood/hardwood/mixedwood forest-group bias, and a hand-recomputed all-forest-types
  rollup) match their source CSVs exactly.
- **Four of five required red-team reframes** are correctly reflected in both the report and the
  deck, using the corrected (not the superseded) framing, with no stale "developing end fixed" or
  "traced to Lever 4" language surviving anywhere checked.
