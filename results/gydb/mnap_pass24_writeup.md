## MNAP survey-year recovery (pass 24)

MNAP's Locations and Plots had been loaded into GYDB with real coordinates, but S_Visits and S_Trees were deliberately left unbuilt because the working CSVs at mnap_raw/ (ERM_ME_AllTrees.csv, ERM_ME_LiveTrees.csv, ERM_ME_Plots.csv, ERM_ME_CSI.csv) carry only an ordinal Round (1 or 2) per plot, with no calendar year anywhere, and S_Visits.YR is NOT NULL in the schema. The candidate fix identified previously was EcoreserveMonitoring.accdb on Aaron's Google Drive (file ID 18RTsKvnGhnuqTYVou53Y5Mz3j-S9bK5G, owned by aaron.weiskittel@maine.edu, 4,173,824 bytes, last modified 2018-07-30), which this pass retrieved and converted.

Retrieval worked on the first real attempt and did not require a turnkey launcher. The Drive connector's download_file_content tool returned the full file as a base64-encoded string for this non-Google-native, application/octet-stream file; the harness saved the 5.5 million character response to a local JSON result file rather than inlining it, and that file was then uploaded byte for byte to Cardinal via cardinal_upload (5,565,230 bytes, matching exactly) and decoded there with a five line Python script. The decoded object is 4,173,824 bytes, identical to the Drive metadata, and Cardinal's file command correctly identifies it as a Microsoft Access Database. The zipped copy and the third party TNC-only copy were not needed and were not fetched.

Conversion needed a working tool, since Cardinal has no mdbtools binary, no root, and cannot reach CRAN. Three options were tested rather than assumed: the pip packages pandas_access and mdb-parser both installed cleanly from pypi.org, confirming general pypi egress, but pandas_access is a thin wrapper that shells out to the same missing mdb-export binary, and mdb-parser (a 2 KB stub package) turned out to be non-functional. The path that worked was compiling mdbtools 1.0.1 from source: Cardinal has gcc, glib2 (including the pkg-config dev files), bison, flex, and the autotools chain already present, and git clone of github.com/mdbtools/mdbtools succeeded (Maven Central and raw.githubusercontent.com are also reachable from Cardinal, which would have supported a jackcess/Java fallback if the C build had failed). `make install` itself failed only because its bash-completion target tries to write to /usr/share, which is read only without root; the actual mdb-export, mdb-tables, mdb-schema, and related binaries built cleanly in the source tree and were copied directly into a user-owned prefix, sidestepping the completion-install failure entirely.

mdb-tables listed 24 tables in the accdb: Deadwood, EcoReserves, Herb, LUP_Browse, LUP_CrosswalkNCEcoSys, LUP_DecayClass, LUP_Growth, LUP_HarvestHist, LUP_HarvestType, LUP_lichen, LUP_NCTypeME, LUP_NCTypeNat, LUP_Town, LUP_TreeCondition, LUP_TreeCrownClass, LUP_TreeDamage, LUP_TreeDmgLoc, MASTER6B, OtherSpecies, PlotMetrics, Plots, Saplings, Seedlings, Trees, and Vascular. PlotMetrics is the table that resolves the ask: it carries PM_ID, Plot_ID, Date, and Round together, one row per plot visit (374 rows total), with real MM/DD/YY dates spanning July 2004 through 2011 for Round 1 and June 2011 through 2016 for Round 2 (Round is therefore a two-bucket label over an eleven-year span, not a stand-in for a single year, which is exactly why the ordinal alone could never have been converted to a year without this table).

The join key turned out to be exact rather than approximate: ERM_ME_LiveTrees.csv and ERM_ME_AllTrees.csv already carry the accdb's own PM_ID and Plot_ID columns, so the recovered dates attach at the individual visit level, not just at the plot level. Validation checked this rather than assuming it: of 3,564 LiveTrees rows whose PM_ID matched a PlotMetrics row, the CSV's own Round value agreed with the accdb's Round value in every single case, zero mismatches. Coverage, however, is partial and is disclosed rather than smoothed over. The 2018 accdb snapshot's PlotMetrics table has only 374 visit records, while the current, evidently more complete CSV extracts reference 1,600 to 1,616 distinct PM_IDs across LiveTrees and AllTrees, so only about 22 percent of the visits in the CSVs resolve to a real date from this file (350 to 354 of PM_IDs, depending on which CSV). The unresolved 78 percent is not a data quality problem on the resolved side; it means substantially more monitoring rounds exist in the current tree data than this eight year old accdb snapshot ever recorded, most plausibly because fieldwork continued after 2018 and the accdb was never updated, or a newer version of the database exists that was not part of this pass's inputs. The third party TNC-only copy (file ID 1mhldJ4v9z-9jUBmBq8My7p97TQESh0i4, 4,395,008 bytes, a different size than Aaron's copy) was not opened this pass and is a plausible next place to look for the missing PlotMetrics rows, though its provenance and schema are unconfirmed and it was flagged as lower confidence at the outset. Separately, two Plot_IDs found in PlotMetrics (509 and 510) do not exist in the MNAP S_Plots rows already loaded from ERM_ME_Plots.csv, so their five combined visit records were excluded rather than inserted against a nonexistent plot; five further PlotMetrics rows had a blank Date or a blank Round and were excluded for the same reason, disclosed rather than guessed at.

With the resolvable subset, S_Visits and S_Trees were built for MNAP (Dataset 8) directly against the existing S_Locations and S_Plots rows, following the same conventions build_gydb.R's build_generic_source function uses elsewhere (Frame assigned from the tree's EXPF against the two frame constants already on file for MNAP's nested design, Status from the accdb's Condition crosswalk with 1 and 2 as live and 3 as dead, species mapped through the six letter MNAP code to the two letter AGY code to the existing AGY2SP crosswalk already used for every other GYDB source). The species crosswalk was parsed directly out of mnap_raw/ERM_ME_SpeciesCodes.R rather than retyped by hand, and every one of the 58 species codes observed in the tree data resolved cleanly to a SpeciesCD already present in Lookup_Species; the 16 rows coded .dead, .deadc, .deadd, .UNID, .DICOT, or blank fell to the standard T_X unknown placeholder, which is the correct, already established behavior for unidentifiable stems rather than a new gap. Height was nulled (not dropped) for 1,201 of 4,098 resolved tree rows because the source recorded a large block of zero or negative values, the same disclosed HT range rule build_gydb.R already applies uniformly to every other source; DBH needed no correction, with a full range of 12.7 to 119.0 cm across the source data. Tree identity used the accdb's own TP_ID directly rather than a synthetic renumbering, since it is a stable per-row key; a real cross-visit tree identity is also present in the source (a TreeLink column plus a New/status flag) that would support true survivor and ingrowth Membership coding in a future pass, but Membership was left NULL this pass rather than interpret ambiguous flag values (N, E, e, ?, n, 7) without confirmation.

Before writing anything, the database was backed up to data/ALL/ALL_Standardized_PREV_20260822b.sqlite (a distinct suffix from the same day's ALL_Standardized_PREV_20260822.sqlite backup taken for the concurrent S_PlotTreatments work), and only S_Visits and S_Trees were touched; S_PlotTreatments and every other table were left exactly as found. The result is 367 new S_Visits rows for Dataset 8 (266 Round 1 visits, 101 Round 2 visits, real years spanning 2004 to 2016) and 4,098 new S_Trees rows, verified against zero foreign key violations on both tables after the insert. The next step to close the remaining gap is either locating a newer or more complete EcoreserveMonitoring accdb than the 2018 snapshot used here (the TNC-only copy is the first thing to check), or asking MNAP/TNC directly for visit dates on the roughly 1,250 PM_IDs that the current CSVs reference but this accdb never recorded.
