## Headline

The session's own starting brief was wrong on two of its four FIRST/THEN items, and the red team caught
both before either propagated further. Job 13340586 needed no resubmission, it had already completed
successfully five days before this session started. The calc_tree_volume crash had nothing to do with the
suspected column collision; the real cause was a self-referential default argument in two taper functions,
a more severe and previously undiagnosed bug that also explains a documented, previously unresolved gap in
the Bakuzis Eichhorn test. Both catches are F9 (inherited wrong numbers) in the OODA firewall sense: a
figure or diagnosis carried into this session from a prior handoff, taken at face value, and shown wrong by
direct instrumentation rather than argued from priors.

On the substance: the r2 plus ingrowth combination is confirmed additive, not synergistic, and closes only
the ingrowth share of the gap, about 2.6 pp on mefia_l via xu25r2. SDImax onset retuned to 0.55 passes
Bakuzis cleanly on its own terms but trades 2.84 pp of mefia_l gain for 2.83 pp of Baxter loss, so it still
needs LEVER 3 before it ships, exactly as pass 6 predicted. Density-dependent recruitment, the machinery
this session was asked to activate as an alternative to a flat multiplier, was already active by default in
every prior sweep, and a reshaped version built this pass made the age 27 to 48 crash worse, not better, so
that direction is closed. The site gradient inertness has a specific, named cause: two opposite-signed site
terms in the plot-level basal area increment equation nearly cancel. The calc_tree_volume fix is verified
and, as a bonus, retired a five-week-old documented limitation in the Bakuzis Eichhorn test, though real
volume changed no PASS/FLAG verdict anywhere.

## F9 catches, detailed

**Job 13340586.** The brief carried into this session read "keeps being PREEMPTED on cpu; resubmit to a
non-preemptible partition," with the fix identified as pointing MODEL_FILE at p4e/model_b0b1b2.r. Direct
sacct query at session start showed all four array tasks COMPLETED, exit 0:0, finishing 2026-08-06 at
07:50 to 07:52, roughly an hour after they started and, per the timestamps, likely before the handoff
describing them as stuck was even written. The MODEL_FILE fix was in fact already applied and is confirmed
correct: task 1's log reads "PATCHED ddbh: b0= -1.88366 b1= 0.49788 b2= -0.0293426," matching ratified r2
exactly. All four result files landed at 919 rows (918 data rows plus header), matching the v131base
benchmark. No resubmission was needed or performed. The lesson carried into the standing warnings below:
a job status claim in a handoff is itself a number subject to F9 and must be re-queried, not re-run blind.

**calc_tree_volume.** The brief's hypothesis, a name collision between the function's internal working
column and a pre-existing `dia` column in the caller's tree.data, was tested directly and refuted: the
crash reproduces identically whether or not tree.data carries a `dia` column. The actual cause is a
self-referential default argument, `function(x = x)`, in `taper_kozak()` and `taper_westfall_scott()`
(and, on inspection, the same dead-code pattern in `calc_dib()`), which R evaluates by forcing a promise
that is already being forced, producing the exact error text on every call regardless of input. A second,
separate defect was found in the process: `calc_merch_height()` wraps its optimizer in `try(silent=TRUE)`,
so the taper crash was being silently swallowed and merch height silently substituted with total tree
height on every call, with no error and no warning. A third defect, real but distinct from the crash, is
the one the original hypothesis actually described: the internal `dia` working column would silently
overwrite a caller-supplied `dia` column if one existed, corrupting data without crashing. All three are
fixed in one overlay, `/users/PUOM0008/crsfaaron/magplot/verify/p8vol/calc_tree_volume_patch.R`, sourced
after the model file, verified by numeric identity (max abs difference 0) against the correct-path
behavior on 192 synthetic points and 200 real trees.

**Downstream risk, checked and closed.** Because calc_tree_volume feeds a TOTVOL bias metric already on
the standing scorecard, the fix's discovery raised an obvious question: were the shipped TOTVOL numbers
(mefia_l -16.53%, memat -7.98%, medev -7.33%, pef -3.83%, ctrn -9.78%, baxter +8.77%) silently wrong.
Checked directly: bench_p6.R and bench_p6score.R never call calc_tree_volume, calc_merch_height, or either
taper function; TOTVOL there is computed by an independent NSVB allometric emulator (`nsvb()`, driven by
nsvb_emulator_coefs.csv), and the model file's own internal call to calc_tree_volume (line 4643) is
commented out, with `use.vol=FALSE` set in the scoring harness besides. The standing TOTVOL scorecard is
unaffected. The bug does reach two places: the Bakuzis trajectory diagnostic (p7bak/traj_p7b.R, wrapped in
tryCatch and silently returning NULL on every call) and, by extension, the Eichhorn relation test, both
addressed below.

r2" with 1.13 pp of the 15.44 pp ceiling. Direct recompute this pass (r2only versus v131base) gives 0.195

xu25Nr2 (SDImax off) was not stress-tested against the pass-6 stem-blowup precedent (a prior SDImax-off

failure, an open item: recommend a targeted rerun with tree-level logging before treating xu25Nr2 as
cleared, though it is not the recommended shipping candidate regardless.

## Track B. SDImax onset retune, validated on its own terms, not yet shippable alone

The controlling parameter is `ops$sdimort.onset` (default 0.30, model lines 4108 to 4121, untouched), with
companion knobs `sdimort.break` (0.62, left at default), `beta.gentle` (0.02), `beta.steep` (0.80), and a
hard ceiling `max` (1.00). Retuned to onset 0.55 and 0.60 in a new overlay, `p8sdi/traj_p8sdi.R`, mirroring
p7bak's trajectory driver exactly. All cells verified at 800 rows against traj_base_initA/B.csv.

At age 160, onset 0.55 and 0.60 both plateau near base: basal area 35.8 to 35.9 m2/ha and SDI 673 to 675,
within 1.3 percent of the base case (35.4 m2/ha, SDI 668), nowhere near the nosdi runaway (50 m2/ha, SDI
about 1020). The ramp still engages; retuning the onset does not collapse it into nosdi behavior. Both
target checks pass.

One correction to how this session's own brief framed the problem: the "full stack" basal area crash
description (14.2 percent drawdown, ages 27 to 48, gain reversing from +14.9 percent at year 20 to -2.9
percent at year 160) is actually the standalone ing39 configuration's behavior, not the literal full stack
(ing2.5 plus nosdi plus r2), which shows no comparable dip because nosdi disables the mechanism that causes
it. Retesting the correctly identified case, ing39 at onset 0.55 versus ing39 at the default 0.30: drawdown
14.4 percent versus 14.2, recovery age 87 to 93 versus 86 to 92. Onset retuning is neutral to marginally
worse on this failure mode, as expected, since it is an ingrowth over-recruitment defect, not a
self-thinning defect.

Bias tradeoff, reusing pass 6's already-verified, balance-closing instrumentation rather than rerunning the
full FIA harness this pass: onset 0.55 alone improves mefia_l from -16.53 to -13.69 percent, a 2.84 pp
gain, matching the 2 to 3 pp estimate in the pass 6/7 handoffs closely. Against that, Baxter worsens from
+8.77 to +11.59 percent, a 2.83 pp loss, confirming the exact masking tradeoff those handoffs warned about:
the too-low onset was hiding a known LEVER 3 survivor-increment over-prediction in mature stands, and
retuning the onset alone unmasks it rather than fixing it.

**Verdict: onset 0.55 does not ship alone.** It is biologically defensible in isolation, passes every
Bakuzis check run against it, and correctly leaves the ing39 crash mode untouched rather than papering over
it. It must ship paired with the LEVER 3 correction, with Baxter rechecked at that point, per the standing
recommendation from two passes ago, now with harder numbers behind it. No run this pass combined onset 0.55
with both r2 and ingrowth 2.5x simultaneously, so the actual shipping candidate's full bias number remains
`[UNVERIFIED: not directly measured, inferred from roughly orthogonal single-lever effects]`.

## Track C. Density-dependent recruitment rejected, site gradient cause found

**Recruitment.** The machinery this session was asked to test, `ops$use.ingrowth.release`,
`ops$ingrowth.rd.center`, `ops$ingrowth.rd.k`, a logistic taper on relative stand density meant to replace
a flat multiplier, turns out to already be default-ON in every prior IMULT sweep cell, including the ones
this project has been calling "flat." A reshaped version, recentered from 0.58 to 0.45 with amplitude
5.81, was calibrated against the real mefia_l relative-density distribution to target a 2.5x population
average multiplier. It overshot to a realized 3.92x, because relative density evolves over the 15-year
projection in a way a static calibration snapshot cannot anticipate, and a fast single-stand trajectory
test showed it makes the age 27 to 48 crash worse, not better: a 16.5 percent drop, against 8.3 percent for
flat 2.5x and 13.1 percent for flat 3.9x. The mechanism is the opposite of what was hoped: a density-release
curve concentrates its largest boost exactly in the low-to-moderate-density, actively-developing stand
regime where the crash already lives. This direction is closed; do not pursue density-dependent recruitment
as a fix for the ing39 crash mode.

**Site gradient.** Traced composite site index (csi) through every growth equation. The height increment
equation carries a small but real site term (coefficient 0.00029415 on csi squared) that alone reproduces
the reported roughly 7 percent height gain from csi 12 to 20. The basal area side is different: the
plot-level basal area increment equation, `plot_ba_incr()`, which by Chapter 10 disaggregation constrains
individual tree growth rather than the reverse, carries two site terms of opposite sign that nearly cancel,
q2 = -0.13355 (main csi effect) and q4 = +0.11753 (csi by relative-density interaction), net -0.016. Because
this plot-level equation overrides the tree-level model through proportional rescaling, its near-zero net
site effect suppresses whatever weaker, non-canceling site signal exists at the tree level. Two other
fitted site pathways (an SDImax csi term and an ESI dominant-height anchor) are both gated off in every
scored configuration. The realized csi range in mefia_l is also narrow, median 14.0, interquartile range
13.2 to 15.9, relative to the 12 to 20 comparison range, which compounds the flatness but is not the root
cause. This is a named, specific, addressable target for the next refit: the q2/q4 cancellation in
plot_ba_incr(), not a data or extrapolation problem.

## Track D and E. Volume fix, and the Eichhorn gap it happened to close

Fix verified as above. As a direct consequence, a documented but previously unresolved limitation in the
Bakuzis Eichhorn test was closed this pass. bakuzis_p7c.R's own header comment and NOTES.md (lines 142 to
150, 240, 311) already stated that Eichhorn ran on a proxy, VOL = 0.45 times BA times HT, because real
volume crashed, and that this proxy is "near-vacuous" and makes "Eichhorn PASS... uninformative," since the
proxy is mathematically identical to the BA-height relationship it is meant to be an independent check on.
The comment explicitly noted the crash was "not fixed here because the model file must not be edited," the
same constraint this session's overlay respects.

With the p8vol patch available, a byte-identical rebuild of the growth trajectory (traj_p8e.R, verified
against p7bak's original by exact match on HT, BAPH, TPH, and the old proxy VOL, max absolute difference
zero across 1920 rows) computed real taper-integrated volume via calc_tree_volume at the same 5-year,
post-density-peak checkpoints already in use, across all six configs including the two blocked ones, nosdi
and full. Real-volume Eichhorn CV runs 1.88 to 3.97 percent, essentially matching the old proxy's 1.9 to
4.2 percent, and stays PASS in all 12 config-by-init cells with no verdict changes anywhere. This confirms
rather than overturns the existing NOTES.md diagnosis: Eichhorn was uninformative because the site gradient
feeding it is nearly inert (the same finding as Track C, reached independently through a different route),
not because the proxy was mismeasuring something real. No shipping decision made this pass or in prior
passes routed through Eichhorn, so this closes a documentation and rigor gap rather than changing any
recommendation.

## Standing recommendation, revised

Ship xu25r2 (ingrowth 2.5x, r2 increment refit, SDImax retained at default onset) as the near-term
candidate; it is additive-only but real, and carries no new risk found this pass. Do not ship SDImax onset

magnitude against intended target where a calibration is involved, row count alone missed a 2.5x-to-3.92x
